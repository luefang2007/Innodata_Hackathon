# Track 1 Team Plan: Coding Task Factory on pallets/click

## What we're building

An automated factory that writes exam questions for AI coding agents.

- **Input:** `pallets/click`, pinned at a release commit.
- **Output:** 5 substantively different feature-development tasks in the Harbor package format. Each task contains:
  - a spec (`instruction.md`)
  - a gold patch (the reference implementation)
  - feature tests that fail on the base repo and pass with the gold (F2P)
  - curated existing tests that pass both before and after (P2P)
  - a Dockerfile
- **Valid task:** gold scores 1.0, the base repo scores 0.0, and the regression tests stay green.
- **Good task:** Claude Haiku 5.5 fails it (resolve@3 of 0/3 or 1/3).
- **The deliverable is the pipeline.** Judges re-run it and score its raw, unedited output.

## How scoring shapes the design

| Dimension | Pts | What it means for us |
|---|---:|---|
| Reliability | 20 | Judges re-run the pipeline and measure first-pass yield, so the pipeline must self-check and only emit packages that pass |
| Difficulty | 20 | Haiku 5.5 should fail most tasks across 3 attempts |
| Variation | 20 | The 5 tasks test different capabilities, and we must explain how the pipeline makes them different |
| Fairness | 15 | Everything a test checks is stated in the spec |
| Efficiency | 10 | Cost per valid task, backed by token logs |
| Regression | 10 | Pick existing tests related to the change, not the whole suite |
| Reproducibility | 5 | Exact Harbor format; re-runs give comparable results |

Every package must also clear 8 gates:

- **Structure:** required files present and `task.toml` parses.
- **Name integrity:** the task differs from others by behavior, not by renamed identifiers.
- **Novelty:** the feature is not already in click upstream.
- **Grounding:** it extends real click modules.
- **Gold:** the gold scores 1.0.
- **Nop:** the feature tests fail on the base repo.
- **Base health:** the untouched repo builds and its suite is green.
- **Mutation:** a broken gold makes the feature tests fail.

## Gotchas to settle first

1. **Lue's Windows laptop has no Docker or Harbor.**
   - Harbor self-checks and the Haiku benchmark run on a teammate's Mac or Linux machine with Docker.
   - Lue's laptop runs the generator and the local fast checks. It needs only Python, git and uv, which are already installed.
2. **network_mode.**
   - `no-network` is fine for the oracle/nop self-check, but the benchmark agent needs network access.
   - The evaluator checks that the benchmarked task matches the submitted task (task_checksum).
   - So generate with the benchmark's setting (`allowlist` or `public`) from the start. Ask the organizers which one.
3. **The materials contradict each other. Ask the organizers:**
   - Benchmark attempts per task: k=3 in the docs, 5 on the kickoff slides.
   - Demo length: 5 minutes on the slides, 10 minutes in SUBMISSION.md.
   - Build window: the rules say 4.5 hours, which ends at 13:50, but the upload deadline is 15:30.

   Until we hear back, assume k=3 and a 5-minute demo.
4. **The gold patch and the test patch must never edit the same file.** Feature tests always go in a new file, `tests/test_<slug>.py`.
5. **`check_structure.py` flags AI or authoring tells** such as "Generated by". The prompts must forbid them.

## Why click

- pytest is fast and the Docker build is quick.
- The kit's worked example is already pytest-based, so its `test.sh`, `grade.py`, `parser.py` and `run_script.sh` work almost unchanged. We disclose this reuse in the README.

## Pipeline

```
0 Setup (once)   click@release -> map extension points + coverage map (which lines each existing test touches)
1 Pick           choose an unused cell in the variation matrix
2 Spec           LLM writes instruction.md: signatures, every rule, edge cases, exact error text
3 Gold + tests   LLM writes the gold (src/ only) + a new test file (tests/ only)
4 Local checks   no Docker, seconds per run:
                 a gold applies cleanly
                 b feature tests fail on the base repo
                 c feature tests all pass with the gold
                 d coverage-selected existing tests pass before and after
                 e mutation: auto-break the gold; the feature tests must catch it
                 f fairness: every value a test asserts appears in the spec
                 g novelty: the feature is absent from click's latest main
                 on failure -> feed the error back to step 3, max 3 retries; log attempts + tokens
5 Package        the kit's grading scripts + a click Dockerfile at base_commit
6 Harbor check   oracle = 1.0, nop = 0.0
7 Difficulty     Haiku 5.5, 3 attempts per task
```

## Variation strategy (20 points, and the core of the writeup)

The variation matrix has two axes. The pipeline picks one cell per task, and no two of the 5 tasks share a module or a behavior shape.

- **Module:**
  - argument parsing (`parser.py`)
  - types (`types.py`)
  - core (`core.py`: Context, Command, Group)
  - help formatting (`formatting.py`)
  - terminal UI and testing (`termui.py`, `testing.py`)
  - shell completion (`shell_completion.py`)
- **Behavior shape:**
  - new input grammar (parse and validate)
  - interaction rules with existing features
  - state and lifecycle (callback order, command chaining)
  - exact output format
  - new public API

## Hard but fair

Difficulty comes from many rules that interact, not from hidden information.

- Each task touches 2 or 3 files.
- Its rules interact with click's existing environment variables, defaults, prompts and `multiple`.
- Each rule gets its own test.
- Every rule is written in the spec, and the fairness check enforces this.
- Haiku 5.5 tends to miss one or two of the interaction rules.

Example task shapes (each must pass the novelty check first):

- A `Duration` type that parses "1h30m" into a timedelta, with bounds and exact error text.
- Occurrence limits for `multiple=True` options, with defined precedence against environment variables and default_map.

## Roles

- **A, Environment** (needs a Docker machine): click Dockerfile, grading-script adaptation, Harbor self-checks. Later runs the Haiku benchmark.
- **B, Generator:** step 2 and 3 prompts, JSON output, retry loop, token logging. Produces `pipeline_run.json`.
- **C, Local checks:** step 4 a to e, including coverage-based selection of existing tests (pytest-cov per-test contexts) and the mutation check.
- **D, Task selection and quality:** variation matrix, novelty check against click main, fairness check. Also reviews whether specs are hard enough.
- **E, Delivery and demo:** README, variation writeup, each member's contribution, at most 5 slides, `validate_submission.py`, demo script, benchmark results table.
